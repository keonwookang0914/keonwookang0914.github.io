Chaos Callback 기반 Physics Transit

문제전이 중에는 출발지의 원본 Actor와 목적지의 복제본이 논리적으로 같은 물체여야 합니다. 그런데 Game Thread에서 둘을 맞추려 하면 세 가지가 걸립니다. 오차는 substep마다 쌓이는데 Game Thread는 프레임당 한 번만 보정해 이미 늦고, 충돌 정보는 Physics Thread에만 있어 둘 중 어느 쪽을 기준으로 삼을지 알 수 없으며, 보정한 값조차 다음 Physics Tick에야 반영돼 또 밀립니다.

해결Chaos::TSimCallbackObject로 Physics Tick 안에 직접 들어갔습니다. Contact Modification 단계에서 포탈 내부 Contact만 비활성화해 벽에 걸리지 않게 하고, PreSolve 단계에서 두 Actor의 속도 · 각속도를 보정해 substep 단위로 동기화를 맞췄습니다.

Primitive Voxelization — 부분 전이 충돌 처리

문제Primitive Collision은 부분적으로 켜고 끌 수 없습니다. 물체가 포탈을 절반만 지나가도 충돌은 전체 형상 그대로 남아, 이미 건너간 부분이 출발지 쪽 벽에 계속 걸렸습니다.

해결런타임에 형상을 쪼개면 비용이 크므로 Editor Time에 1회만 Bake하도록 했습니다. Simple Collision을 FKBoxElem 배열로 변환해 WPVoxelData에 저장해 두고, 전이가 시작되면 Voxel BodySetup으로 교체한 뒤 포탈 접평면을 기준으로 Box 단위로 Enable/Disable 합니다.

Material Clipping — 전이 중 시각 처리

문제물체가 포탈을 지나는 동안, 아직 넘어가지 않은 뒷부분이 목적지 쪽에서 비쳐 보였습니다. Material에서 픽셀을 잘라내야 하는데 잘라낼 기준(포탈 중심 · 입구 방향 · 반지름)을 픽셀 셰이더까지 넘길 통로가 좁은 것이 문제였습니다.

해결Custom Primitive Data float4 한 칸에 전부 담기 위해, Portal Center(12byte)에 더해 Entry Normal은 Octahedral Normal로, Radius는 FP16으로 인코딩해 압축했습니다. 셰이더는 포탈 중심에서 픽셀 월드 위치로 가는 벡터 V를 구해, Dot(V, Entry Normal) >= 0 이면서 |V| > Radius인 픽셀만 렌더링합니다.

Voxel 병목 분석 — GameThread Stall의 원인 규명

문제Voxel 개수가 늘어날수록 프레임 드랍이 비선형적으로 심해졌습니다. 체감만으로는 어디가 막히는지 알 수 없어 측정이 먼저 필요했습니다.

해결Unreal Insights(-trace=default, Counters)로 Voxel 4,096개를 프로파일링했습니다. 전이 중 MoveComponent가 부르는 UpdateOverlaps가 Compound Body의 모든 Shape를 순회하며 Overlap Query를 돌리고 있었고, Link된 포탈의 Twin Actor에서도 같은 처리가 일어나 GeomOverlapMultiple과 UpdateOverlaps가 Voxel 개수의 2배만큼 호출되고 있었습니다.

수동 Overlap Query + Chunk 기반 최적화

문제원인은 엔진이 Voxel 하나하나를 전부 질의한다는 데 있었습니다. Voxel을 줄이면 충돌 정밀도가 떨어지므로, 개수는 유지하면서 질의 횟수만 줄여야 했습니다.

해결Voxel Body를 Generate Overlap Events = false로 두어 엔진 자동 계산에서 아예 빼고 필요한 질의만 직접 했습니다. Voxel을 격자로 묶어 Chunk를 만들고 활성 Chunk만 병합해 Box 몇 개로 압축한 뒤, 그 Box에만 OverlapMultiByChannel을 호출하고 이전 프레임 결과와 Diff해 Begin/EndComponentOverlap을 직접 발생시킵니다. 512~8,000 Voxel 전 구간 평균 17.2배(94.2% 감소), 8,000 Voxel 기준 138배(2,639.6ms → 19.1ms/frame, 99.3% 감소)로 개선했고, 최적화 전 최악의 단일 프레임 4,168.9ms가 최적화 후 평균 19.1ms가 됐습니다.

Post Process — Ping Pong 구조로 텍스처 고정

문제Post Process는 읽을 SRV와 쓸 RTV가 동시에 필요한데, D3D11은 같은 텍스처를 둘로 함께 바인딩하면 에러조차 내지 않고 SRV 바인딩을 조용히 NULL로 풀어버립니다(디버그 레이어를 켜야 경고가 보입니다). 그래서 패스마다 다른 텍스처가 필요했고 패스 N개에 텍스처 N+1장이 들었는데, 정작 각 텍스처가 실제로 쓰이는 구간은 한 패스뿐인데도 VRAM은 프레임 내내 잡고 있었습니다.

해결패스 A의 결과를 Texture 2에 쓰고 나면 Texture 1은 더 이상 필요 없다는 점에 착안해, 다 쓴 텍스처를 다음 패스의 RTV로 되돌려 쓰는 Ping Pong 구조로 바꿨습니다. 패스 개수와 무관하게 2장으로 고정됩니다(단순 체인 기준이며, 원본을 다시 봐야 하는 패스는 한 장을 더 잡습니다).

Post Process — Viewport 간섭을 UV Clamp로 차단

문제그 주차 엔진은 Viewport 여러 개가 렌더 타깃 텍스처 한 장의 영역을 나눠 쓰는 구조였습니다. 그래서 Post Process를 걸면 옆 Viewport의 픽셀이 현재 Viewport 연산에 섞여 들어왔습니다. 구조 자체를 바꾸는 게 정답이지만 다른 팀원들과 병렬로 작업하는 중이라 손댈 수 없었고, 현재 구조에서 남에게 영향을 주지 않는 방법이 필요했습니다.

해결상수 버퍼에 현재 Viewport의 원점 · 크기를 실어 보냈습니다. Scene Color · Depth는 전체 텍스처에 들어 있으니 전체 UV로 읽고, World 좌표 복원에는 Viewport Local UV를 쓰되, 샘플링 UV를 Viewport 경계로 Clamp해 침범을 막았습니다.

GPU Skinning — 행렬 패킹 불일치를 1회 Transpose로 해결

문제엔진의 행렬 정책은 row-vector 규약 + 행 우선 저장(float M[4][4])이고 HLSL 기본 패킹은 열 우선이라 #pragma pack_matrix(row_major)로 맞춰 두고 있었습니다. 그런데 이 지시어는 uniform 파라미터가 대상이라 StructuredBuffer에는 적용되지 않았고, 열 우선이 그대로 남아 스키닝된 메시가 깨졌습니다. StructuredBuffer는 fxc가 문법 오류(X3000)로 막고 /Zpr 플래그도 StructuredBuffer에는 걸리지 않아, 선언으로 푸는 길은 둘 다 닫혀 있었습니다.

해결한 정점이 최대 Bone 4개의 가중 합으로 변형된다는 점과, 전치가 선형 연산이라 합과 순서를 바꿔도 된다는 점을 이용했습니다. 루프를 돌 때마다 전치하지 않고 가중 합이 끝난 뒤 마지막에 1회만 Transpose하도록 바꿔, 셰이더 수정만으로 해결했습니다.

GPU Skinning — Bone AABB 근사 + Lazy CPU Skinning

문제CPU Skinning일 때는 변형된 정점이 메모리에 있어 렌더링 · Ray Picking · Bounds가 같은 배열을 공유했습니다. GPU Skinning으로 옮기자 변형 정점이 CPU에 없어져, Picking이 쓰는 정점과 AABB가 BindPose 크기로 고정됐습니다. 정확한 AABB를 위해 매 Tick 전체 정점을 다시 Skinning하면 크기는 맞지만 전 정점 순회가 그대로 병목이 됩니다.

해결매 프레임 필요하지만 근사해도 되는 Broad Phase와, 클릭 시에만 필요하지만 정확해야 하는 Narrow Phase로 나눴습니다. 전자는 Bone에 영향받는 정점을 감싸는 Bounds를 미리 만들어 두고 꼭짓점 8개에만 SkinMatrix × WorldMatrix를 곱해 O(정점 수)를 O(Bone 수)로 줄였고, 후자는 포즈가 바뀐 뒤 첫 호출에서만 CPU Skinning을 1회 수행한 뒤 Möller–Trumbore로 삼각형 교차를 판정합니다. AABB 구성 기준 23.212ms → 0.027ms(Debug Build · 정점 48,705 · Bone 90).

폼 점유율 체크 — 성능과 정확도의 절충

문제기획 요구 중에 스프레이로 스폰한 폼이 파손 구역을 일정 범위 이상 덮어야 수리가 되는 기믹이 있었습니다. 파손 구역이 최대 50개라 최악의 경우 매번 50곳의 점유율을 재야 했고, 부피를 정확히 계산하면 Tick 부하가 감당이 안 됐습니다.

해결점과 폼의 교차 검사가 참이면 그 점은 폼에 닿았거나 내부에 있다는 뜻이므로, 부피 판정을 점 비율 판정으로 근사했습니다. 파손 구역 Box에 점 27개를 잡고 폼에 포함된 점의 비율이 기준치를 넘는지만 보고, 검사 주기도 0.5초로 늘려 부하를 줄였습니다.

패키징 빌드 전용 크래시 — DisplayName 자동 변환

문제에디터에서는 멀쩡한데 패키징한 게임에서만 특정 아이템을 장착하면 크래시가 났습니다. 에디터에서 재현되지 않으니 로그부터 다시 봐야 했습니다.

해결원인은 언리얼이 DisplayName을 따로 지정하지 않으면 사람이 읽기 좋게 문자열을 자동 변환한다는 데 있었습니다. FoamGun이 PIE에서는 'Foam Gun'으로 표기되지만 게임 빌드에서는 'FoamGun' 그대로라, 인자로 넘긴 Label과 일치하는 값이 없어 터진 것이었습니다. UMETA(DisplayName = "...")로 열거형이 에디터에서 어떻게 표기될지 직접 지정해 두 환경의 문자열을 일치시켰습니다.
